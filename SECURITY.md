## Honest Security Disclosure

We believe in transparency. Here is exactly what our security measures do and don't do:

### What We Actually Implement

| Feature | Implementation | What It Does |
|---------|---------------|--------------|
| **Email validation** | Format check only (regex) | Rejects malformed emails. Does NOT send confirmation links. |
| **API key storage** | SHA-256 hash | Server stores key hash, not plaintext. Plaintext returned once at creation. |
| **Signatures** | HMAC-SHA256 | Proves report was generated by our server. Requires server private key. |
| **Rate limiting** | IP + device + global quota | Three-layer: per-IP hourly, per-device hourly, global daily. |
| **IP parsing** | Trusted proxy whitelist | Only trusts X-Forwarded-For from known proxy IPs (127.0.0.1, private ranges). |
| **IDOR protection** | API key hash scoping | Reports filtered by owner's key hash. Cross-user access returns 403. |
| **Report IDs** | Full UUIDv4 | 128-bit entropy. Not sequential, not timestamp-based, not enumerable. |
| **Input validation** | Schema + sanitization | Rejects prototype pollution, homoglyph emails, oversized payloads. |
| **verify_url** | Summary + hash only | Public endpoint shows risk counts, not tool details. Requires hash parameter. |

### What We Do NOT Implement

| Claimed Feature | Actual Status |
|----------------|---------------|
| "Email verification" | **Format validation only.** No confirmation email sent. |
| "Cryptographic signature" | **HMAC-SHA256 commercial integrity marker.** Not Ed25519 attestation. |
| "Device fingerprint" | **Header-based hash** (User-Agent + Accept-Language + Accept-Encoding). Not persistent. |
| "Unbreakable rate limiting" | **Best-effort.** Proxy pools with rotating headers can still bypass device limits. |

### Known Limitations

1. **Static keyword matching** — The 5 risk rules use pattern matching against tool names and descriptions. False positives are expected. Every report includes calibration: "approximately X may be false positives."

2. **No runtime analysis** — We analyze tool metadata, not execution behavior. A tool named `get_weather` could theoretically do anything at runtime.

3. **No supply chain verification** — We don't verify the MCP server's dependencies, build process, or deployment environment.

4. **File-based persistence** — Rate limit counters use JSON files, not Redis. Multi-instance deployments need external state management.

5. **No email delivery** — We validate email format but never send emails. "Check your inbox" messages in API responses are aspirational, not actual.

## Data Collection

### What We Store

| Data | Storage | Retention |
|------|---------|-----------|
| API key | SHA-256 hash only | Until revoked |
| Email | SHA-256 hash only | 24 months |
| Scan metadata | Report ID, timestamps, risk counts | 90 days |
| Rate limit counters | IP hash + endpoint + count | 1 hour rolling |
| Company/role (from /register) | Plaintext | 24 months |

### What We Don't Store

- MCP server source code
- Tool implementation details (only name + description)
- Full scan payloads after report generation
- IP addresses in plaintext (hashed for rate limiting)

## Telemetry

### Hosted Version (api.correctover.com)
- All API calls logged for rate limiting and abuse prevention
- Scan metadata stored for user history
- Lead data (email, company) stored for enterprise follow-up

### Self-Hosted Version
- **ZERO external calls.** No telemetry. No phone-home.
- All data stays on your machine.
- Source code is auditable (Apache-2.0).

To verify: `grep -r "fetch\|http\|https" src/scanner.js` — the self-hosted scanner makes no outbound requests.

### Bypass Resistance

| Attack Vector | Mitigation | Residual Risk |
|---------------|-----------|---------------|
| X-Forwarded-For spoofing | Trusted proxy whitelist | Low — only believed from known proxy IPs |
| Proxy pool rotation | Device fingerprint + global quota | Medium — rotating headers can bypass device limit |
| Multiple email addresses | Global daily quota | Low — caps total keys regardless of email |
| Concurrent requests (TOCTOU) | File-based atomic increment | Low — race window is microseconds |

## CCS Signatures

### What They Are
HMAC-SHA256 signatures using a server-side private key. The signature covers:
- Report ID
- API key
- Timestamp
- Summary data
- Tool list

### What They Prove
- The report was generated by our server (authenticity)
- The report hasn't been modified since generation (integrity)

### What They Don't Prove
- The scan results are accurate (static keyword matching has false positives)
- The MCP server is actually secure (we only analyze metadata)

### Verification
Public `verify_url` endpoint accepts a partial hash parameter and returns:
- Risk counts (summary only)
- Timestamp
- Verification status

Full report details require API key authentication.

## Security Best Practices for Users

1. **Don't share your API key** — It's tied to your usage quota
2. **Store keys securely** — CLI stores in `~/.mcp-scanner/config.json` with mode 600
3. **Use HTTPS in production** — API keys in plaintext HTTP are compromised
4. **Review scan results manually** — Automated scanning is a starting point
5. **Upgrade to Pro for compliance** — Free tier is for development/exploration
6. **Self-host for full control** — Apache-2.0 allows it, zero telemetry
